How Theobase Works

A global, offline-first church management platform for Seventh-day Adventist grassroots operations, built on Cloudflare's edge.

Design Principles

The four principles that shape every decision in Theobase.

System Does the Work

Humans approve. The system populates, computes, and derives — never expect users to compile data by hand.

Self-Teaching

No manual needed. The UI guides first-time users through their tasks with inline prompts and progressive disclosure.

Zero-Assembly Reporting

Every report is derived from live data. Annual statistical reports, tithe remittances — all auto-generated, never hand-compiled.

Surface, Don't Wait

Proactive intelligence. "Giving is down 12% this quarter." "The annual report is ready for review." — surfaced before you ask.

Platform Architecture

The entire system runs on Cloudflare's edge — zero traditional servers, zero containers.

Event-Sourced Church State

Every church is a Durable Object. Its state is not stored in a database — it's reconstructed from a cryptographically chained append-only log.

Write Path: Offline-First Mutations

Every write is an asynchronous intent. The PWA works offline with IndexedDB, then flushes to the server when connectivity returns.

Counting Room: Dual-Signoff Batch Workflow

Financial integrity requires two independent counters to confirm every giving batch before the treasurer commits it.

Membership Lifecycle State Machine

Every member moves through exactly six states. Invalid transitions are rejected by the Durable Object.

Authentication: Passwordless Magic Links + MFA

No passwords. Users authenticate via single-use magic links sent to their email. Financial roles require TOTP-based MFA.

User enters email → Worker sends magic link
via Cloudflare Email → 10-min expiry
single-use (KV) → User clicks link

TOTP MFA required

Dual cookie delivery: httpOnly (automatic) + non-httpOnly (for offline Service Worker header attachment). Refresh every 24h. tokenVersion increment invalidates all sessions on role change.

Role-Based Access Control

14 roles, each with explicit per-operation permissions enforced by both the Worker and the ChurchDO.

Proactive Intelligence

The ChurchDO doesn't wait to be asked — it computes insights from live state and surfaces them to the dashboard.

Backup Verification: Monthly Restore Drill

Every month, a cron trigger picks a demo church, replays its entire event log into a fresh Durable Object, and compares the state hashes. Failure triggers a P1 alert.

Cron Trigger
1st of month → Pick demo church → Replay all events
into fresh DO → Compare state
hashes → ✓ Match → log to D1
✗ Mismatch → P1 alert

This validates that every DO's state is fully reconstructable from its event log and that the hash chain is intact.

Technology Stack

Platform

  • Cloudflare Workers (API Gateway)
  • Durable Objects (per-church state)
  • D1 (cross-church analytics)
  • R2 (photos, docs, backups)
  • Queues (async error ingestion)
  • KV (rate limiting, magic links)
  • Email Routing (transactional)

Backend

  • TypeScript + Hono
  • Drizzle ORM + Zod
  • Append-only event log
  • SHA-256 hash chain
  • 37 operation types
  • 14 roles, per-op permissions
  • Finite state machine (6 states)

Frontend

  • React 19 + TypeScript
  • TanStack Router + Query v5
  • TanStack Table v8
  • Tailwind CSS v4 + shadcn/ui
  • i18next (en + Fijian Hindi)
  • IndexedDB WAL (offline)
  • WebSocket + HTTP sync

Security

  • Passwordless magic links
  • RS256 JWT (7-day session)
  • TOTP MFA for financial roles
  • Defense in depth (Worker + DO)
  • Tamper-evident event chain
  • Data classification (PII isolation)
  • Right-to-erasure redaction
