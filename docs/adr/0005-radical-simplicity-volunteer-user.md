# Radical simplicity: the user is a volunteer

Theobase's primary user at the grassroots is a volunteer church treasurer or clerk, often not technically skilled. Usability is therefore the dominant design constraint, not raw capability. The denomination's own church-management system (ACMS) was abandoned by Fiji's churches because it was too hard to use, and a system that is not radically simple will meet the same fate.

Consequence: when simplicity and capability conflict, simplicity wins. Workflows must be achievable by an untrained user in a few shallow steps, and the system must be forgiving of human error except where policy genuinely forbids it.

Many churches are rural, so the grassroots device is a phone, not a desktop. Theobase is phone-first at the church level, with the desktop experience reserved for the mission office.

ACMS failed at the grassroots for concrete reasons theobase must not repeat: it needs internet (dead offline), demands too many steps and fields for a simple action, speaks administrative jargon, and has login/permission friction. Theobase's anti-spec is: works offline, few steps and fields per action, plain language, and frictionless account provisioning — with a phone experience at least as good as ACMS's.
